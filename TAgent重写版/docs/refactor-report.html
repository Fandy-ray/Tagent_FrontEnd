01效率：三处能量到的提升

全部为本机实测，方法写在每张表下面。

1.1 改一个纯工具函数，不再需要加载整个 AI 栈

旧代码里，Markdown 清洗的 179 行、prompt 模板的 128 行、文本工具、上游错误翻译， 全都住在 rag_utils.py 里。想跑一个只涉及正则的单测，Python 也得先把 langchain、langgraph、openai、faiss、pydantic 全部导入一遍。

你想改的东西旧：必须导入新：只需导入变化
Markdown 表格 / LaTeX 修补5138 ms6 ms801× 更快
出题 / 判卷 prompt 模板5327 ms149 ms35.6× 更快
provider 数据结构40 ms28 ms1.5× 更快
试卷缓存 / 并发闸门25 ms25 ms持平
请求参数校验171 ms175 ms持平
整卷 pydantic schema148 ms152 ms持平

方法：子进程墙钟时间取 5 次最小值，减去解释器空转基线（28 ms）。持平的三项在旧代码里本来就是独立模块—— 提升恰好只出现在 God Class 被拆开的地方，这正是应该出现的地方。

1.2 加第二个服务，不再意味着第二份向量索引

实测一次冷启动预热的构成：

预热步骤耗时说明
import KnowledgeBase4.19 slangchain / faiss 等重依赖
切块 chunks()0.18 sbook1.md → 2178 个切块
建索引 ensure_index()117.71 s嵌入模型 + FAISS，占 96%
合计122.07 s常驻内存约 960 MB

旧结构里，聊天、出题、判卷都挂在同一个 LangChainRAGSimulator 实例上—— 只要还是"一个类装下全部"，这份开销就只付一次。问题出在想加第四种能力的时候： 再 new 一个 simulator，就是再付 122 秒和 960 MB。

新结构里 KnowledgeBase 和 ModelClientFactory 由 app/container.py 建一次，注入三个 service。加第四个 service 时把同一个实例传进去即可， 增量成本为零。测试里有一条断言专门盯着这件事： 

# test_main_routes.py
self.assertEqual(len(created), 1, "三个 service 必须共用同一个 KnowledgeBase")
self.assertIs(services.chat.knowledge_base, created[0])
self.assertIs(services.quiz.knowledge_base, created[0])
self.assertIs(services.exam.knowledge_base, created[0])

1.3 顺手修掉一个会静默重建索引的兜底分支

重构中发现的缺陷

旧 route_utils.get_agent_service() 在 current_app.extensions 取不到服务时，会当场 new 一个新的 LangChainRAGSimulator （连带一个独立的 ModelClientFactory）并塞回 extensions。

这个分支一旦被走到，就是在请求处理过程中同步建一份新的 FAISS 索引： 按上表就是阻塞 122 秒、再吃 960 MB，而且旧的 HTTP 连接池被悄悄换掉。 新的 deps.get_services() 直接读 extensions，没有这个分支—— 装配失败就是启动失败，不会伪装成一次很慢的请求。

03接入 OpenNotebook 与新 RAG

这是重构真正的回报所在。

重构前，"换一个知识来源"要动 rag_utils.py——那个文件里检索、出题、判卷、 Markdown 清洗、prompt 模板互相缠着，改检索会同时暴露在出题和判卷的代码路径上， 而覆盖它们的测试要靠 object.__new__ 绕过构造函数才能造出替身。

现在三个 service 只依赖一个对象，通过 7 个方法与知识来源打交道：

KnowledgeBase 方法被谁用接 OpenNotebook 时
retrieve(query)ChatService · QuizService必须实现
search(query, k=3)ExamService（解答题补材料）必须实现
chunks()QuizService（选片段出题）必须实现
sample_exam_context(topic)ExamService（三段出卷）必须实现
warm_up()启动预热可空实现
ensure_index()内部可空实现
quiz_documents()便捷封装可继承默认
这个接缝已经被验证过

不用等到接 OpenNotebook 才知道行不行——测试里已经这么干了。 tests/test_review_exam_wiring.py 里的 FakeKnowledgeBase 只实现了 3 个方法，ExamService 就能完整跑通出卷与判卷； test_rag_concurrency.py 里的 QuizKnowledgeBase 更极端—— 它的 ensure_index() 直接 raise，用来断言"出题绝不该触发建向量库"。 这些替身就是 OpenNotebook 适配器的原型。

三种接法，改动都局限在一两个文件

A. 整体替换——知识全部来自 OpenNotebook：

# 1) 新增 app/rag/opennotebook_kb.py，实现上表前 4 个方法
# 2) app/container.py 改一行：
-   knowledge_base = KnowledgeBase(text_db_dir=..., knowledge_file=...)
+   knowledge_base = OpenNotebookKnowledgeBase(base_url=settings.notebook_url)

B. 组合——本地教材 + OpenNotebook 一起检索，这是更可能的形态：

# app/rag/composite_kb.py
class CompositeKnowledgeBase:
    def __init__(self, *sources): self.sources = sources

    def retrieve(self, query):
        parts, docs = [], []
        for s in self.sources:
            c, d = s.retrieve(query)
            parts.append(c); docs += d
        return "\n\n---\n\n".join(parts), docs
    # search / chunks / sample_exam_context 同理 fan-out

# container.py：
knowledge_base = CompositeKnowledgeBase(
    KnowledgeBase(),                     # book1.md
    OpenNotebookKnowledgeBase(...),      # 笔记库
)

04怎么验证的

重构最大的风险是"看起来没坏"，所以验证方式列在这里备查。

新旧服务并排跑同一批真实请求

旧代码起在 :5098，新代码起在 :5099，配同一个 DeepSeek provider， 发同一批请求，比对状态码 + JSON 结构（键路径与类型的集合）—— LLM 文本不确定，所以比形状不比内容。

组覆盖结果
admin 通道注册 provider、列表、Key 脱敏3/3
真实 LLM 调用chat 非流式 / SSE 流式 / rag / 出题 / 判题5/5
内部通道临时 provider envelope、缓存失效3/3
错误路径400 / 403 / 404 / 410 / 413 / 4226/6
整卷路径三段并发出卷 + 本地/LLM 分批判卷结构一致

整卷那一项额外断言了公开投影不泄漏答案字段 （accept / correct_index / reference_answer / rubric）—— 两边都干净。SSE 流对比的是帧序列特征：首帧 delta 键、末帧 finish_reason、[DONE] 结尾。

常驻的架构守卫

basic-agent/tools/check_architecture.py，纯标准库，无新依赖：

  1. 引用了但没定义也没 import 的名字
  2. 未使用的 import
  3. 分层依赖方向
  4. 配置收口：os.getenv 只允许在 app/config.py
  5. Flask 只允许出现在 app/api/ 与启动类
  6. controller 不得 import 兄弟 controller

规则 1 不是凑数的——重构过程中它抓到了两次真实缺陷： upstream_errors.py 漏搬 OutputParserException（会让 502 映射变成崩溃）， exam_prompts.py 漏搬 TYPE_SHARE_BOUNDS。 第一个是靠测试发现的，第二个是这个检查器在测试之前就报了出来。 

cd basic-agent && python -m tools.check_architecture
架构检查通过：48 个模块，6 项规则全部满足。

05没有改进的地方

避免这份报告读起来像广告。

  • 请求延迟一点没变，也不该变。瓶颈是上游模型， 对照测试里两边的耗时差异全部落在 LLM 的正常波动范围内。
  • 代码总量没减少（3833 → 3883 行）。删掉的只有 5 个零调用方的死方法 和 2 个死函数，其余是搬家。
  • app/schema/exam.py 仍有 637 行。它是整卷的 pydantic 模型群， 本身内聚，硬拆只会制造循环依赖，所以没动。
  • 试卷缓存仍是单进程内存实现。ExamCache 依赖 waitress 单进程多线程； 要多进程部署仍需换共享存储。重构把它归位到 repository/，让替换有了明确落点，但没有替换。
  • 出卷仍慢（实测 13–19 s，长材料可到 100 s 以上）。 app/config.py 里那段压测注释说得很清楚：提速要靠调度，不是改 prompt。
  • 预热仍要 122 秒。索引没有落盘缓存，每次启动重建。 这是接 OpenNotebook 之后值得优先解决的问题——届时数据量只会更大。
下一步建议

在接 OpenNotebook 之前先给 KnowledgeBase 加索引持久化 （FAISS save_local / load_local + 内容哈希失效）。 现在只需要动一个文件；等来源变成两个再做，就要同时处理两套失效逻辑。
