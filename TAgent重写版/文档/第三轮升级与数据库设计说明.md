# 第一部分　数据库设计

## 一、为什么要加数据库

之前后端没有数据库：对话、批改、成绩只存在学生自己的浏览器里——老师看不到学情，学生换电脑、清缓存就全没了。

对数据库的要求：

1. **数据不能丢**（最基本）：已经保存成功的数据，程序崩溃、重启后必须一条不少。
2. **数据多了也要快**：按百万条记录的量来测。
3. **扛得住一个班同时用**。
4. **方便**：保持「双击 start 一键启动」，不额外装软件。
5. **macOS、Windows、Linux 都能跑**。

## 二、选型：比了 6 种，选 SQLite

### 1. 怎么比的

- 按真实使用情况造数据：**100 万条对话**（2000 名学生、40 个班）+ **2 万篇论文批改**。
- 每种库测同样的内容：批量写、逐条写、按编号读、查某学生最近 20 条、按班级算平均分、改、删、多人同时访问、**强制杀掉进程后数据还在不在**、占用多少磁盘和内存、备份要多久。
- macOS 本机实测一遍，Linux 环境再测一遍；Windows 做了分析。

### 2. 结果一览

| 方案 | 崩溃后数据 | 逐条写（条/秒） | 查最近 20 条（次/秒） | 多人同时（次/秒） | 要额外装服务吗 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **SQLite** | ✅ 一条不丢 | **11,214** | **16,236** | 约 1,000~3,300 | 不用 | **选它** |
| PostgreSQL | ✅ 一条不丢 | 4,504 | 6,167 | 7,000~10,000（最强） | 要 | 以后多台服务器时再换 |
| MongoDB | ❌ 默认设置会丢 | 8,656 | 1,888 | 5,200~7,200 | 要 | 不选 |
| MySQL | ✅ 一条不丢 | 1,251 | 1,933 | 1,800~4,000 | 要 | 不选 |
| DuckDB | ✅ 一条不丢 | 924 | 361 | 400~670 | 不用 | 统计快，日常读写弱 |
| SurrealDB | ✅ 一条不丢 | 5,623 | 56 | 约 250 | 要 | 不选 |

（数字为 Linux 环境、100 万条数据下的实测值）

### 3. 为什么是 SQLite

1. **数据最稳**：两个平台各做单条、成批两种崩溃测试，已保存的数据一条没丢，成批写入也没有出现「只写进去一半」；重启后立刻可用。
2. **单机最快**：按编号读、逐条写、改、删都是第一，比 PostgreSQL 快 2~6 倍——它就在后台程序里面，不用走网络。
3. **最省事**：Python 自带，不用安装、不用单独启动服务、不依赖 Docker；整个库就是一个文件，备份 1.6 秒。
4. **够用**：每秒约 1000 次操作，按每次对话 3 次操作、每人 10 秒问一次估算，能撑约 3000 人同时在线；真正限制并发的是出题批改服务那一侧，不是数据库。
5. **跨系统最稳**：服务端数据库在 Windows 上大多要靠 Docker，而 Docker 在学校机房、老师电脑上不一定能开；SQLite 只要 Python 能跑就能用。

它的局限：同一时刻只能有一个写入者；库文件不能多台机器共享。**要部署多台后端服务器，或长期每秒上千次写入时，换 PostgreSQL**（表结构和查询基本通用）。

## 三、表结构

一共 5 张表（第 2 版）：

| 表 | 存什么 | 主要字段 |
| --- | --- | --- |
| `students` 学生 | 每台设备一条 | 设备编号、昵称、第一次 / 最近一次使用时间 |
| `chat_turns` 答疑记录 | 每问一次一条 | 学生、模式（课程答疑 / 论文助手）、提问、回答、**是否答完**、用了哪些笔记本、耗时、时间 |
| `essay_reviews` 论文批改 | 每次交稿一条 | 学生、题目、原文、总分、完整批改结果（三个维度、逐句批注、总评）、时间 |
| `exam_attempts` 整卷 | 每张卷一条 | 试卷编号、学生、卷面、作答、得分、总分、出卷时间、交卷时间 |
| `exam_cache` 试卷（第三轮新增） | 出好的试卷（含答案） | 试卷编号、出卷时用的服务、试卷内容、过期时间（2 小时） |

- **索引**：所有「某学生最近的记录」都按（学生，时间）建索引；老师看的平均分按（学生，分数）建覆盖索引——不建的话一个统计要 1 秒左右，建了只要几十毫秒。
- **批改结果、卷面、作答**这类嵌套内容直接存成 JSON 文本，SQLite 能直接查询。
- **表结构升级**：库里记着版本号，程序启动时按顺序自动升级（第三轮就是从第 1 版自动升到第 2 版，旧数据原样保留）。

## 四、几个关键设计

| 问题 | 怎么做的 |
| --- | --- |
| **怎么知道是谁** | 平台没有登录：每台设备第一次打开时生成一个匿名编号，连同设置里填的昵称一起带给后台。它只是「同一台设备」的标记，不是账号 |
| **会不会拖累正常使用** | 不会。记录是「尽量记」：数据库打不开、被占用、磁盘满，都只在日志里记一笔，答疑和批改照常；单次记录额外耗时约 0.4 毫秒 |
| **连点、刷新会不会记重复** | 不会。同一个学生重复提交的同一个请求只处理一次、只记一条 |
| **临时对话** | 一条都不记（界面上承诺过「不保存」） |
| **放在哪** | 系统的应用数据目录，不放在项目文件夹里（项目常在会同步的桌面上，正在写的库被同步容易坏）。macOS：`~/Library/Application Support/TAgent/`；Windows：`%LOCALAPPDATA%\TAgent\`；Linux：`~/.local/share/tagent/`。可以用 `TAGENT_DB_PATH` 指定别的位置 |
| **备份** | 同目录下 `backups/`：每天自动备一份、保留最近 7 份；备份不停服务。演示前也可以手动备份一次 |
| **老师怎么看** | 两个查询接口：全班概览（每个学生提问数、批改数、平均分）、某个学生最近的答疑 / 批改 / 整卷记录。需要管理员口令 |
| **不想记录时** | 设置 `LEARNING_STORE=0` 即可关闭 |
| **服务重启了正在考的试卷怎么办**（第三轮） | 出好的试卷同时存进 `exam_cache`，重启后学生照样能交卷、能判分 |

## 五、验证过什么

- 强制杀掉进程（`kill -9`）：已保存的记录一条不少，库文件完整性检查通过。
- 16 个线程同时写：一条不少、没有报错。
- 30 个学生同时提问：记录 30 条，一条不多一条不少、没有记错人。
- 同一学生回答到一半连刷 20 次：20 条都如实记成「没答完」。
- 备份文件能正常打开；两个备份同时触发会排队、失败不留残片；库文件损坏时服务照样能启动。
- 「把修复临时撤掉，对应测试必须报错」的反向检验全部通过。

# 第二部分　第三轮升级

## 一、背景

- 队友在 `fronted` 分支上做了设置面板、多语言和三套新配色，这一轮先合并进来。
- 合并后做了一次完整的代码检查，查出 15 个问题，其中几个会直接影响课堂使用（检索不到笔记、学习记录记错人等）。
- 之后按「最没耐心的用户」和「最差的网络 / 服务状况」做极端测试，并专门处理速度。

## 二、问题修复（15 个）

### 1. 影响使用的

| 问题 | 现象 | 修好后 |
|---|---|---|
| 选「全部笔记本」检索不到东西 | 选了之后回答里一条笔记内容都没有 | 正常检索全部笔记本 |
| 归档的对话恢复不了 | 点「取消归档」没反应，归档的对话也打不开 | 能恢复、能打开 |
| 设置里「数据」页列表是空的 | 已归档、已分享的对话一条都不显示 | 已修；演示版里这一块按队友方案隐藏，归档的对话统一从用户菜单「已归档对话」管理 |
| 第一次打开配色不对 | 先是蓝灰配色，进答疑页又跳成暗色 | 一开始就是暗色 |
| 英文系统上界面半中半英 | 一部分文字按浏览器语言变成英文 | 默认简体中文 |
| 保存账号信息后报错 | 昵称存上了，但弹窗关不掉 | 正常保存、关闭 |

### 2. 学习记录准确性

| 问题 | 修好后 |
|---|---|
| 两个同学同时点「生成整卷」会拿到同一张卷，交卷后记录互相覆盖 | 每个人拿到自己的卷，记录各归各 |
| 两个同学交同一篇范文，后交的人没有记录 | 两人都有记录 |
| 「临时对话」界面写着不保存，后台却照样记录 | 临时对话一条都不记 |
| 回答因网络中断没说完，却记成「已完成」 | 如实记成「未完成」 |

### 3. 稳定性与细节

- 浏览器里存的设置出了问题时，所有请求都会失败 → 现在不影响正常使用。
- 回答过程中每秒都把全部聊天记录重新保存一遍，聊天多了会卡 → 现在只存正在显示的那一条。
- 手动备份和自动备份撞在同一秒可能出错，备份失败会留下残留文件 → 已排队处理、失败自动清理。
- 两个服务进程同时第一次打开数据库会出错 → 已修。
- 主题切换的代码有三份重复，设置面板指定打开某一页时可能空白 → 已合并、已修。
- 前端类型检查清到 0 错误。

## 三、极端情况测试

### 1. 测了什么、结果如何

| 场景 | 结果 |
|---|---|
| 回车连按 12 下发问 | 只发出 1 次 |
| 回答显示到一半，连续刷新 5 次 | 已显示的内容保留，标注「没有完成」，可以一键重新生成 |
| 回答到一半切到别的对话 | 内容不会串到别的对话 |
| 「交稿批改」同一瞬间点 8 下 | 只批改 1 次，只记 1 条 |
| 「生成整卷」连点 8 下 / 「提交试卷」连点 8 下 | 都只处理 1 次 |
| 整卷答到一半连续刷新 3 次 | 卷子和已写的答案都在，不会重新出卷 |
| 30 个同学同时提问 | 全部正常，记录一条不多一条不少 |

### 2. 测出来的 5 个新问题（都已修好）

| 问题 | 怎么修的 |
|---|---|
| 批改中刷新后点「重新批改」，结果出来了却还提示「没有完成」 | 重新批改时清掉上一次的中断标记 |
| 整卷题目上方的提示句里，公式显示成 `$\lambda$` 这样的原始代码 | 答题页、结果页都改成正常显示公式 |
| **整卷答到一半服务重启，交卷提示「试卷不存在」，答案白写** | 试卷同时存进数据库（`exam_cache` 表），重启后照样能交卷、判分 |
| 卷子真的过期（超过 2 小时）后，刷新还会回到那张交不了的卷子 | 认出过期后清掉，直接给「重新出卷」 |
| **全班同时交稿，6 个人里 4 个提示「请求过多」** | 满了先排队（最多 30 秒、8 人）。实测 6 人、10 人同时交全部成功 |

另外，**笔记本服务开着却卡住时，每个问题要等 32 秒才出第一个字** → 出错的服务先暂停使用、在后台检测恢复，第一个字 1.6~2.4 秒就出来。

## 四、速度提升

| 项目 | 之前 | 之后 |
|---|---|---|
| 答疑页第一次打开 | 1.26 秒（159 个请求、2.5 MB） | **0.12 秒**（35 个请求、142 KB） |
| 测评页第一次打开 | 0.45 秒（2.1 MB） | **0.08 秒**（98 KB） |
| 一键启动 | 约 30 秒 | **11 秒** |
| 教材检索准备时间（每次启动） | 23.2 秒 | **0.78 秒** |
| 笔记本服务卡住时，第一个字出现 | 32 秒 | **1.6~2.4 秒** |

主要做法：启动脚本改用打包好的正式版前端（改代码时可用 `--dev` 切回开发模式）；教材检索的准备结果存到本机，教材一改自动重新生成；公式显示、设置面板等按需加载；前端打包和后台启动同时进行。

## 五、怎么确认改对了

- 后台自动测试全部通过；前端类型检查 0 错误；打包正常。
- 反向检验：把每一处修复临时撤掉，对应测试必须报错——全部报错，说明这些测试真能防止问题再出现。
- 上面的连点、刷新、切换、重启场景都在真实浏览器里实际点过；压力测试脚本全部重跑通过。

# 第五部分　复查之后的修复与新功能

## 一、一句话总结

修好了试用中反馈的「选中一句点『解释』却说没选中」和「回答里的公式、加粗不显示」；
范例文章入库、《系统仿真学报》14 篇论文接进了出题 / 答疑 / 批改的检索；
顺带查出两个影响很大的隐藏问题——**笔记本一直没真正接上**、**刚启动时一群人同时提问后台会崩**——都已修好。

## 二、试用中反馈的问题（都已修好）

| 问题 | 原因 | 修好后 |
|---|---|---|
| 在批改的卷子里选一句，点「解释」，发出去的是「未选中文本」 | 画了线的句子点一下会高亮，看起来像选中了，其实没有选中文字 | 点中的画线句子也算选中；什么都没选时提示「先选中一段文字」，不再发一句空话出去 |
| 点「提问」再点取消，照样发出去了 | 取消被当成了「什么都没填」 | 点取消就什么都不发 |
| 回答里的公式原样露出 `\frac{…}`，「一个**“…”的实验**」露出两个星号 | 回答的显示不认公式；中文引号旁边的加粗按英文排版规则不算数 | 公式正常排版；中文标点旁边的加粗正常显示 |
| 一键启动看起来像跳过了前端打包 | 打包在后台进行，提示要等后面才打印 | 开始打包时就打印一行 |

复查时又挑出 6 处细节一并改了：加粗里带代码或链接时显示乱、「参考文献 [1]」被当成公式、换到别的回答下面点「解释」还会用到之前点过的句子等。

## 三、新功能

### 1. 范例文章入库

「论文助手」里「填入范例」用的文章，自己写的现在随代码一起提交，大家拉代码就有。
期刊、教材等别人的文章，文件名改成 `xx.local.txt`，只留在自己电脑上——仓库是公开的，不能转载。

### 2. 《系统仿真学报》论文作为参考材料

- **用在哪**：出题、答疑、论文批改查材料时，除了教材，还会查这 14 篇论文。问到具体课题会查到对应的论文（例如问呼叫中心排班就会查到那一篇），泛泛的课程问题仍以教材为主。
- **选了哪些**：和课程最贴近的 14 篇——排队与服务台配置 5 篇（呼叫中心排班、仓储机器人配置、地铁楼梯宽度、休假排队、仿真结果的验证方法）、工具与建模方法 4 篇、其他建模思路 5 篇。每篇都打开官网核对过题目和卷期。
- **版权怎么处理**：期刊官网写的是「版权所有」，没有开放转载。所以仓库里只放**篇目清单**，全文在每个人第一次启动时从期刊官网下到自己电脑上（约 23MB、半分钟左右），以后启动直接跳过。
- **网络不好时**：连不上期刊官网就跳过，十秒内照常启动，下次再补。
- **加论文**：期刊上的，在篇目清单里加一项，大家下次启动都会下到；手头的 PDF，直接放进 `basic-agent/references/` 文件夹，只在自己电脑上生效。

## 四、查出的隐藏问题（影响大，已修好）

| 问题 | 怎么发现的 | 原因 | 修好后 |
|---|---|---|---|
| **笔记本从来没真正接上**：笔记本服务开着，启动时却提示「笔记本连不上」，答疑只用到了教材 | 想把检索加进启动脚本时追查到的 | 开着 Clash 之类系统代理的电脑上，后台连本机的笔记本服务也被送进了代理，代理返回错误 | 本机和局域网的地址一律直连；实测启动后显示「笔记本已连上」 |
| **刚启动时一群人同时提问，后台会崩溃或卡死** | 暴力测试：16 个检索同时到达 | 检索程序第一次运算如果是多个请求同时做的，会出错：3 次里 2 次后台进程直接退出、1 次卡住十几分钟。第三轮加了「启动走缓存」以后，第一次运算落到了学生的第一个问题上 | 启动时先单独算一次，之后再并发；实测新启动的后台 32 个提问同时到，连试 5 次全部正常 |
| 「解释」连点 8 下，同一个问题问了 8 遍 | 暴力测试 | 正在回答时再点会排队，同一句排了 7 条 | 同一句正在答或已在排队就不再排；连点 8 下只问 1 遍 |
| 网络不通时启动被拖两分钟 | 断网测试 | 下载论文时每篇都要等满超时 | 先试一下期刊官网通不通，不通就跳过：120 秒 → 10 秒 |

## 七、对大家的影响与待办

**对大家的影响**
- 第一次启动会多等一会儿：下载论文半分钟、整理检索材料一分钟左右，只有第一次。
- 开着系统代理的电脑，现在笔记本里的内容才真正能被查到。
- 选「全部笔记本」时，教材、论文、笔记本三处一起查；选了某个笔记本时只查那个笔记本。

**待办 / 需要协助**

| 事项 | 说明 | 建议 |
|---|---|---|
| Windows 启动脚本没有实测 | 下载论文这一步在 `start.ps1` 里也加了，但手上没有 Windows 环境 | 请有 Windows 电脑的同学跑一次 |
| 笔记本服务按关键词查找 | 本机的笔记本服务没配语义查找，只能按关键词找 | 需要时在笔记本服务里配置 |
| 开机自启服务不会自动下载论文 | `deploy/` 下的配置不经过启动脚本 | 部署时手动运行一次下载脚本 |
| 论文里的表格、公式抽出来是乱的 | 只影响检索时附带的那段原文 | 暂不处理 |
| 英文正文的那一篇（交叉口掉头）查得不太准 | 检索偏向中文内容 | 暂不处理 |
