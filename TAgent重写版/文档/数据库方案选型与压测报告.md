# 数据库方案选型与压测报告

> 日期：2026-10-01 ｜ 测试平台：macOS 实测、Linux 实测（Docker 容器）、Windows 分析 ｜
> 测试脚本与原始数据：`TAgent重写版/basic-agent/tools/dbbench/`

## 结论先说

**推荐 SQLite 作为 TAgent 的主存储**，配三样东西：WAL 模式、两行调优参数、给统计查询建覆盖索引。
将来要部署到多台服务器、或者全校规模长期高并发，再换 PostgreSQL。

理由（数据见后文）：

1. **持久化最基础的一关**：SQLite 在 macOS、Linux 上各做单条提交、成批事务两种崩溃测试，**已确认的写入一条没丢，也没出现半批**，
   库文件完整性检查通过，重启即恢复（0 秒）。六个方案里只有 **MongoDB 默认配置没过**（4 轮崩溃都丢了已确认的数据）。
2. **单机读写删改最快**：调优后，Linux 上按主键读每秒 10.6 万次、查某学生最近 20 条每秒 1.6 万次、单条写每秒 1.1 万次，
   都是第一，比 PostgreSQL 快 2~6 倍——因为它就在应用进程里，没有网络往返。
3. **最方便**：Python 自带，不用装、不用起服务、不依赖 Docker；一个文件就是整个库，备份 1.6 秒；macOS / Windows / Linux 一样用。
4. **并发够用**：单进程并发上限约每秒 1000~1800 次数据库操作（其他方案里只有 PostgreSQL、MongoDB 明显更高）。
   按每次对话约 3 次数据库操作估算，能撑住上千名同时在线的学生——真正的瓶颈是大模型那边只放 2 个并发调用，不是数据库。

它的短板要心里有数：**同一时刻只能有一个写者**、库文件不能被多台机器共享、复杂统计要靠建对索引（否则一个班级平均分要 1 秒）。

## 背景与要求

后端现在没有数据库：对话、批改、成绩都只存在学生自己的浏览器里，老师看不到学情，换设备、清缓存就丢。
选型要求：

1. **数据持久化**（最基础）：已经确认写入的数据，进程崩溃、服务重启后必须一条不少。
2. **大数据量下读写删改快**：百万级记录。
3. **扛得住并发**：一个班、几个班同时用。
4. **方便**：安装、部署、备份简单，符合现在「双击 start 一键启动」的交付方式。
5. **跨操作系统**：macOS、Windows、Linux 都要能跑（现在已有 start.command / start.bat / start.sh）。

## 候选方案

| 方案 | 类型 | 怎么跑 | 一句话特点 |
| --- | --- | --- | --- |
| **SQLite** | 嵌入式关系库 | Python 自带，一个文件 | 零安装、零运维；同一时刻只能一个写者 |
| **DuckDB** | 嵌入式分析库 | `pip install`，一个文件 | 列式存储，统计分析极快；并发小事务弱 |
| **PostgreSQL** | 服务端关系库 | 单独起服务（Docker / 安装包） | 并发、功能、生态最全；要多运维一个服务 |
| **MySQL** | 服务端关系库 | 单独起服务（Docker / 安装包） | 国内最常见；默认配置保守 |
| **MongoDB** | 服务端文档库 | 单独起服务（Docker / 安装包） | 存 JSON 最自然；没有表结构约束 |
| **SurrealDB** | 服务端多模型库 | 单独起服务（Docker） | **OpenNoteBook 已经在用它**，可以复用同一个服务 |

没有列入实测的：Redis（内存键值库，适合做缓存，没有二级索引和查询能力，不适合做主存储）；
JSON 文件（模型登记现在就这么存，没有事务，并发写会互相覆盖）。
SurrealDB 的 Python SDK 2.0 自带嵌入式引擎，也能像 SQLite 一样不起服务，本次只测了服务端模式（复用 OpenNoteBook 那个）。

## 测试方法

**数据**按 TAgent 的真实负载造，固定随机种子，每个库拿到的完全一样：

- 对话消息：**100 万条**，2000 名学生、40 个班，每条 80~400 字，约三成带分数；索引：（学生，时间）、（班级）
- 小论文批改：**2 万篇**，原文 1200~2500 字 + 批改结果 JSON（三个维度 + 5 条批注）约 2~3 KB

**测试项**（每个库都用自己推荐的写法和官方驱动）：

| 维度 | 测什么 |
| --- | --- |
| 写 | 批量写 100 万条（每批 5000，SurrealDB 每批 1000）；批量写 2 万篇作文；单条写 5000 次、每条一个事务（学生一条条发消息） |
| 读 | 按主键读 2 万次；查某学生最近 20 条 5000 次（答疑页、学情页最常用）；按班级算平均分（老师看板）；全文模糊搜索；读一篇作文并解析批改 JSON |
| 改 / 删 | 单条改、单条删各 5000 次；批量改、批量删各 10 万条（每批 1000）；最后核对总数（全部 ✅） |
| 并发 | 8 / 32 / 64 个线程各 10 秒，混合负载：70% 查最近 20 条、15% 新增、10% 改分、5% 读作文。32 正好是 basic-agent 的服务线程数 |
| **持久化** | 写入进程每提交成功一次就记一笔「已确认」，然后 **kill -9**：嵌入式库杀应用进程，服务端库杀数据库服务本身；重启后核对「已确认」的是否一条不少。另测 5000 条一批的事务：崩溃后不能只剩半批 |
| 资源与运维 | 磁盘、内存、启动时间、安装体积、备份耗时 |

**环境**：Apple M3（8 核）、16 GB 内存。服务端库都跑在 Docker 里，每个容器限 4 核 / 2 GB，测谁只开谁；嵌入式库在测试进程里。
**所有库都用默认配置**，只有 SQLite 另加一组「调优」（原因见下文）；调参对其他库的影响单独说明。

- **macOS**：本机实测。服务端库经 Docker Desktop 端口转发访问——这就是在 Mac、Windows 上用 Docker 部署的真实情况。
- **Linux**：测试程序放进同一 Docker 网络里的 Linux 容器（Debian 13，限 4 核 / 4 GB）再跑一遍，对应部署到 Linux 服务器。
- **Windows**：这台机器测不了，只做分析（见「跨操作系统」）。

## 结果

### 1. 持久化：只有 MongoDB 默认配置丢了数据

| 方案 | 单条提交：崩溃后丢失 / 已确认 | 5000 条一批：丢失 / 已确认 | 半批 | 恢复可用 |
| --- | --- | --- | --- | --- |
| ✅ SQLite | 0 / 44,952 | 0 / 75,000 | 0 | 0.00 秒 |
| ✅ SQLite（调优） | 0 / 44,275 | 0 / 85,000 | 0 | 0.00 秒 |
| ✅ DuckDB | 0 / 7,550 | 0 / 65,000 | 0 | 0.68 秒 |
| ✅ PostgreSQL | 0 / 12,763 | 0 / 90,000 | 0 | 1.88 秒 |
| ✅ MySQL | 0 / 2,229 | 0 / 60,000 | 0 | 2.06 秒 |
| ❌ MongoDB | 143 / 13,764 | 0 / 95,000 | 0 | 2.75 秒 |
| ✅ SurrealDB | 0 / 10,068 | 0 / 35,000 | 0 | 0.86 秒 |
| ❌ MongoDB 默认 `w:1`（再测 3 轮） | 71、64、164 / 13,638、13,973、14,343 | — | — | — |
| ✅ MongoDB `journal=true`（3 轮） | 0、0、0 / 4,232、5,551、5,104 | — | — | — |

- 其余方案在崩溃后**已确认的数据全部还在**，成批事务**没有一次只进去半批**；SQLite 两个平台的完整性检查都是 ok。
- **MongoDB 默认的写入确认（`w:1`）不等日志落盘就回「成功」**，日志约每 100 毫秒才刷一次，崩溃时这段窗口里的写入就没了——
  4 轮测试每轮都丢了 64~164 条。改成 `journal=true` 后 3 轮都不丢，但单条写从每秒 5686 条降到 2183 条（慢 62%）。
- 测的是「进程 / 服务崩溃」。**断电**这台机器模拟不了：PostgreSQL、MySQL 默认每次提交都刷盘；
  SQLite 用的 `synchronous=NORMAL`（WAL 模式的推荐配置）在断电时可能丢最后几次提交，要断电也不丢就改 `synchronous=FULL`（写入会变慢）。

### 2. 读写删改速度（100 万条数据，Linux）

加粗的是这一行最好的。表里 SQLite 用的是调优配置（默认配置的数字见附录）。

| 操作 | SQLite（调优） | DuckDB | PostgreSQL | MySQL | MongoDB | SurrealDB |
| --- | --- | --- | --- | --- | --- | --- |
| 批量写 100 万条（秒） | 35.6 | 37.8 | 29.1 | 40.8 | **26.0** | 62.7 |
| 单条写（条/秒，每条一个事务） | **11,214** | 924 | 4,504 | 1,251 | 8,656 | 5,623 |
| 按主键读（次/秒） | **105,655** | 6,375 | 18,527 | 6,424 | 7,669 | 6,148 |
| 查某学生最近 20 条（次/秒） | **16,236** | 361 | 6,167 | 1,933 | 1,888 | 56 |
| 读一篇作文并解析 JSON（次/秒） | **55,884** | 5,726 | 8,214 | 4,853 | 6,608 | 4,407 |
| 单条改（次/秒） | **11,784** | 1,577 | 2,797 | 1,194 | 6,707 | 5,089 |
| 单条删（次/秒） | **7,190** | 1,584 | 2,763 | 1,178 | 2,526 | 3,384 |
| 批量改 10 万条（条/秒） | 17,886 | **49,169** | 12,291 | 6,207 | 21,209 | 18,545 |
| 批量删 10 万条（条/秒） | 9,738 | **92,610** | 22,537 | 4,757 | 16,870 | 6,067 |
| 全文模糊搜索（毫秒/次） | **1.2** | 3.0 | 14.1 | 1.8 | 3.2 | 6.8 |

- **SQLite 在单线程的读、写、改、删上全面领先**：它就在应用进程里，没有网络往返；这也正是 basic-agent 的用法。
- **批量改 / 删 DuckDB 最快**（列式存储、批处理引擎），**批量写 MongoDB、PostgreSQL 最快**。
- **SurrealDB 查「某学生最近 20 条」每秒只有 56 次**：它用上了索引，但会把这个学生的全部 421 条读进内存再排序取前 20（不排序只要 2 毫秒）。
- macOS 上的结果排序一致，完整数字见附录 A。

**为什么 SQLite 要调优**：默认页缓存只有 2 MB，百万行的库随机读几乎每次都要读文件，在 macOS 上尤其慢
（默认配置按主键读每秒只有 9 千次，Linux 上是 11.6 万次）。加两行参数就解决：

```sql
PRAGMA mmap_size = 268435456;   -- 256 MB 内存映射
PRAGMA cache_size = -65536;     -- 64 MB 页缓存
```

同一个库文件在 macOS 上：按主键读 9 千 → **19.8 万次/秒（22 倍）**，查最近 20 条 2.5 千 → 2.2 万次/秒，
读作文 6.8 千 → 5.9 万次/秒；崩溃测试照样零丢失。代价是进程内存从约 106 MB 升到约 470 MB（内存映射计入进程内存）。

### 3. 并发：PostgreSQL 最强，SQLite 够用

混合负载下每秒完成的操作数，以及 p99 延迟（100 次里最慢那次的水平）。

| 方案 | macOS 8 / 32 / 64 线程（次/秒） | macOS p99（毫秒） | Linux 8 / 32 / 64 线程（次/秒） | Linux p99（毫秒） | 出错 |
| --- | --- | --- | --- | --- | --- |
| SQLite（调优） | 3,295 / 1,872 / 1,696 | 6 / 33 / 72 | 1,897 / 1,056 / 1,066 | 9 / 56 / 109 | 0 |
| DuckDB | 670 / 646 / 648 | 41 / 207 / 351 | 388 / 414 / 417 | 69 / 196 / 394 | 0 |
| PostgreSQL | 8,764 / 10,208 / 9,718 | 2 / 8 / 20 | 7,169 / 8,199 / 8,237 | 2 / 11 / 23 | 0 |
| MySQL | 1,821 / 3,270 / 3,927 | 42 / 45 / 80 | 4,051 / 2,893 / 2,858 | 16 / 35 / 58 | 0 |
| MongoDB | 7,172 / 6,607 / 6,223 | 2 / 42 / 59 | 5,845 / 5,373 / 5,207 | 4 / 18 / 37 | 0 |
| SurrealDB | 239 / 240 / 246 | 80 / 305 / 647 | 281 / 261 / 252 | 57 / 275 / 686 | 0 |
| SQLite（调优+写锁） | 2,718 / 1,817 / 1,734 | 6 / 33 / 66 | 1,922 / 1,066 / 1,068 | 9 / 54 / 105 | 0 |

- **PostgreSQL 并发最强**：每秒 7000~10000 次，64 线程 p99 也只有 20 毫秒左右；MongoDB 次之。
- **SQLite 单进程每秒约 1000~3300 次**，线程越多延迟越高（64 线程 p99 70~110 毫秒），但**全程零报错**。
  我们试过在应用里加一把写锁让写入排队，结果几乎一样——瓶颈是单个 Python 进程里的串行化，不是 SQLite 抢锁，所以不用加。
- **够不够用**：按每次对话约 3 次数据库操作、一个活跃学生平均 10 秒发一次消息估算，每秒 1000 次能撑住约 3000 名同时在线的学生；
  而大模型那边只放 2 个并发调用，数据库远不是瓶颈。
- **DuckDB、SurrealDB 不适合这种负载**：每秒只有几百次，64 线程 p99 分别到 0.4 秒、0.7 秒。

### 4. 统计查询：索引比选哪个库更重要

「按班级算平均分」是老师看板的典型查询（100 万条里约 30 万条有分数）：

| 方案 | 按班级算平均分：macOS | Linux |
| --- | --- | --- |
| SQLite | 1,001.6 毫秒 | 898.9 毫秒 |
| SQLite（调优） | 1,034.4 毫秒 | 1,295.6 毫秒 |
| DuckDB | 1.2 毫秒 | 1.5 毫秒 |
| PostgreSQL | 79.8 毫秒 | 86.8 毫秒 |
| MySQL | 5,217.1 毫秒 | 5,204.2 毫秒 |
| MongoDB | 634.1 毫秒 | 602.1 毫秒 |
| SurrealDB | 3,528.1 毫秒 | 3,530.9 毫秒 |

- **DuckDB 1~2 毫秒**，列式引擎天生适合统计。
- SQLite、MySQL 慢是因为**查询规划器挑了只有 `class_id` 的索引，再逐行回表**。补一个覆盖索引 `(class_id, score)` 后：
  **SQLite 852 → 23 毫秒，MySQL 4868 → 72 毫秒**（macOS 实测）。结论：学情看板的每类统计，都要按查询条件建对应的覆盖索引。
- MySQL 另一个原因是默认缓冲池只有 128 MB；SurrealDB 3.5 秒是其查询引擎本身的水平。

### 5. 资源与运维

| 项目 | SQLite | DuckDB | PostgreSQL | MySQL | MongoDB | SurrealDB |
| --- | --- | --- | --- | --- | --- | --- |
| 要额外起服务吗 | 否 | 否 | 是 | 是 | 是 | 是（可复用 OpenNoteBook 的） |
| 安装体积 | 0（Python 自带） | 驱动 20 MB | 镜像 411 MB + 驱动 7 MB | 镜像 1.09 GB + 驱动 22 MB | 镜像 1.12 GB + 驱动 1 MB | 镜像 101 MB + 驱动 6 MB |
| 启动到可用 | 立即 | 立即 | 1.0 秒 | 5.0 秒（首次初始化） | 1.0 秒 | 0.8 秒 |
| 崩溃后恢复 | 0 秒 | 0.3~0.7 秒 | 1.9 秒 | 2.1 秒 | 1.3~2.8 秒 | 0.9 秒 |
| 磁盘（100 万条 + 2 万篇） | 1.1 GB | 0.53 GB | 2.0 GB | 3.1 GB（含 binlog，两轮后涨到 4.2 GB） | 0.9~1.1 GB | 1.3 GB |
| 内存 | 在应用进程内（调优后约 470 MB） | 在应用进程内（约 1 GB） | 146~199 MB | 534~618 MB | 220~686 MB | 355 MB~1.1 GB |
| 备份方式 | 在线备份 API / 拷文件 | EXPORT DATABASE / 拷文件 | pg_dump | mysqldump | mongodump | surreal export |
| 备份耗时（大小） | **1.6 秒**（1.1 GB） | 1.0 秒（247 MB） | 18.8 秒（142 MB） | 2.7 秒（878 MB） | 30.0 秒（150 MB） | 20.1 秒（937 MB） |

- 内存与磁盘是测完那一刻的量；服务端库的内存受「每个容器 2 GB」的限制。
- MySQL 8 默认开着 binlog（二进制日志，默认留 30 天），同一个库连跑两轮后磁盘涨到 4.2 GB；不需要主从复制可以关掉。

## 跨操作系统

**macOS 与 Linux 实测结论一致**（完整数字见附录 A、B），差异有两处：
SQLite 默认配置在 macOS 上读得慢（原因见上，调优后解决）；服务端库在 macOS 上要经过 Docker Desktop 的端口转发，单次往返更慢。

**Windows 这台机器测不了，以下是分析**：

| 方案 | Windows 上怎么装 | 需要注意 |
| --- | --- | --- |
| SQLite | Python 自带，什么都不用装 | 数据文件别放网络盘 / 共享盘（文件锁在网络盘上不可靠）；杀毒软件实时扫描会拖慢写入，可把数据目录加白名单 |
| DuckDB | `pip install duckdb`（有 Windows 版） | 同上；同一个库文件同时只能被一个进程打开 |
| PostgreSQL | 官方安装包装成 Windows 服务，或 Docker | 装服务要管理员权限，学校机房电脑常常没有 |
| MySQL | 官方 MSI 装成服务，或 Docker | 同上 |
| MongoDB | 官方 MSI 装成服务，或 Docker | 同上 |
| SurrealDB | 官方二进制，或 Docker | 复用 OpenNoteBook 那个就依赖 Docker |

关键在 **Docker**：Windows 上的 Docker Desktop 要开 WSL2 或 Hyper-V，需要 BIOS 开虚拟化和管理员权限，比赛、机房、老师自己的笔记本都不一定满足。
现在 start.bat / start.command 在 Docker 没开时会跳过 OpenNoteBook、照样把答疑和测评拉起来——
**如果数据库放进 Docker，这条退路就没了**：Docker 一起不来，连成绩都存不了。嵌入式方案没有这个问题：Python 能跑，它就能跑。

## 推荐方案与接入要点

**主存储用 SQLite**，接入时注意：

1. 连接参数：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout`，再加上文两行 `mmap_size` / `cache_size`；每个线程各用一个连接。
2. 表：学生、会话、消息、批改记录（原文 + 结果 JSON）、试卷与答题、成绩。批改结果这类嵌套数据直接存 JSON 文本，SQLite 自带 JSON 函数能查。
3. 索引：按查询建。「某学生最近 N 条」建（学生，时间）；老师看板的每类统计建覆盖索引（例：（班级，分数））。
4. 备份：每天用在线备份 API 拷一份（100 万条 1.6 秒，不停服务），保留最近 7 份。库文件**不要放在 iCloud / OneDrive 同步目录或网络盘上**
   ——项目本身就在桌面上，所以默认放到系统的应用数据目录，而不是项目文件夹里。
5. 表结构升级：用 `PRAGMA user_version` 记版本号，启动时按顺序执行升级脚本。

### 已经接进 basic-agent（2026-10-01）

| 项 | 做法 |
| --- | --- |
| 记什么 | 答疑每一轮（提问、回答、qa / paper 模式、是否答完）、论文批改（原文、题目、分数、完整批改 JSON）、整卷（卷面、作答、得分） |
| 记给谁 | 平台没有登录：前端给每台设备生成匿名编号，连同设置里的昵称放在请求头里（`X-Tagent-Client-Id` / `X-Tagent-Client-Name`）。只是设备标记，不是身份认证 |
| 不影响主流程 | 记录全部「尽力而为」：库打不开、被占用、磁盘满，只记日志，答疑和批改照常；启动时库打不开也照常起服务（`/health` 里 `learning_store: off`） |
| 不重复记 | 记录写在请求合并的「领头那次」里：连点、刷新重交、90 秒内重放，都只记一条 |
| 放在哪 | macOS `~/Library/Application Support/TAgent/tagent.sqlite3`；Windows `%LOCALAPPDATA%\TAgent\`；Linux `~/.local/share/tagent/`。可用 `TAGENT_DB_PATH` 改 |
| 备份 | 同目录 `backups/`，每天一份、留 7 份（`LEARNING_BACKUP_KEEP`）；老师也可以手动 `POST /admin/learning/backup` |
| 老师查看 | `GET /admin/learning/summary`（全班概览）、`GET /admin/learning/students/<编号>`（某人最近记录），要管理员口令 `X-Agent-Admin-Token` |
| 关掉 | `LEARNING_STORE=0` |
| 忙等待 | 2 秒（不是 30 秒）：记录是附加功能，宁可丢一条记录也不让学生多等 |

代码：`app/repository/learning_store.py`（库）、`app/api/learner.py`（认人、记一笔）、`app/api/learning_admin.py`（老师接口）；
前端 `src/lib/data/learner.ts`。测试 `tests/test_learning_store.py`、`tests/test_learning_api.py`（含 kill -9 崩溃、16 线程并发、备份可用、库损坏仍能启动）。

**什么时候换 PostgreSQL**：要部署多台后端服务器（SQLite 文件不能跨机器共享）；或者长期每秒上千次写入；或者要让别的系统远程直连数据库。
表结构和 SQL 基本通用，迁移成本可控。

**其他方案为什么不选**：

- **DuckDB**：统计分析极快（班级均分 1~2 毫秒），但并发小事务每秒只有几百次，内存占约 1 GB。可以将来当「只读分析」的补充——它能直接读 SQLite 库文件。
- **MySQL**：默认配置下单条写每秒只有 800~1250 次，统计要 5 秒，磁盘占用最大，镜像 1.09 GB；没有胜过 PostgreSQL 的地方。
- **MongoDB**：并发不错，但**默认配置崩溃会丢已确认的数据**；要改 `journal=true`，写入慢 62%；镜像 1.12 GB。
- **SurrealDB**：复用 OpenNoteBook 的服务看起来省事，但批量写最慢、「最近 20 条」每秒 56 次、并发只有约 250 次/秒、内存占用最高；
  而且和 OpenNoteBook 共用一个库，一方升级或出问题会连累另一方。

## 测试的局限

- 单台机器（Apple M3）；服务端库跑在 Docker Desktop 的虚拟机里，限 4 核 / 2 GB，都是默认配置。专门调参后（如 MySQL 加大缓冲池）数字会不同。
- 测试程序是 Python，和 basic-agent 一样受全局解释器锁影响；嵌入式库和测试程序在同一进程，这正是它们在 basic-agent 里的真实形态。
- 断电没有模拟，只测了进程 / 服务崩溃。
- Windows 没有实测。

## 附录 C　怎么复现

脚本在 `TAgent重写版/basic-agent/tools/dbbench/`，本次原始数据在同目录的 `results-2026-10-01/`。

1. 在该目录建一个独立虚拟环境并装驱动（不动项目自己的依赖）：`duckdb psycopg[binary] mysql-connector-python pymongo surrealdb psutil pandas`
2. 起服务端库（容器名 `dbbench-*`、端口 55432 / 53306 / 57017 / 58000，各限 4 核 / 2 GB，放在 `dbbench-net` 网络里）
3. `./run_mac.sh sqlite: sqlite-tuned: duckdb: postgres:dbbench-postgres mysql:dbbench-mysql mongo:dbbench-mongo surreal:dbbench-surreal`
4. Linux：准备 `wheels-linux/`（各驱动的 Linux arm64 安装包）后 `./run_linux.sh ...`（参数同上）
5. `./backup.sh`、`./mongo_journal.sh`，最后 `python summarize.py mac|linux` 出表

国内网络下 Docker Desktop 若拉不下镜像，可用 `pull_image.py` 经本机代理下载后 `docker load`。
